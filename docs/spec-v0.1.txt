Overview
Mei is a 3D fantasy console modelled on PlayStation-era hardware: a small RISC CPU, a
vector unit for geometry, and a GPU that only fills 2D triangles. "Mei" ( 明 , "bright", written
as sun plus moon) is a working name. The Sun/Moon theme is branding only and has no
effect on the hardware.
Design goals:
The look comes from the hardware rules. Affine textures, pixel-snapped vertices,
sort-based depth and dither are how the machine works, not post-effects.
Limits are real. A cycle budget, a triangle limit and fixed memory sizes are enforced by
the machine.
Deterministic. All math is fixed-point and input is sampled once per frame, so a cart
runs identically everywhere.
Runs in a browser tab. The emulator is C compiled to WebAssembly.

The GPU is a software rasterizer that draws 2D triangles into a 320×240 framebuffer; it

Dither. When bit 0 of GPU_CTRL  is set, the GPU adds an offset from a 4×4 matrix to each
8-bit channel, clamps, then drops the low 3 bits. The offset is chosen by the pixel's x and y
modulo 4. The proposed matrix is the one the PlayStation used:
Texture tinting. A texel is multiplied by the polygon colour, where 128 means unchanged.
Values above 128 brighten, up to double, and results clamp at 255.
Transparency. Palette index 0 is never drawn. Semi-transparent packets blend with the
framebuffer using one of four modes (see GPU packets).
Budget. The GPU draws at most 2,000 triangles per frame. Extra triangles are dropped
and a status bit is set. Drawing costs no CPU cycles.
CPU
The CPU is a 32-bit RISC core with fixed 32-bit instructions, little-endian, with no floating
point, no flags register, no delay slots and no interrupts. Branches compare two registers
and jump in one instruction.
Scalar registers. There are 16, r0 – r15 , each 32 bits. r0  always reads zero and ignores
writes.
Vector registers. There are 8, v0 – v7 , each holding four 32-bit lanes named x, y, z, w.
Lanes normally hold 16.16 fixed-point values. All eight are general-purpose; the transform
instruction reads its matrix rows from v4 – v7 .
Fixed-point. A 16.16 value is a signed 32-bit integer where 65,536 represents 1.0. fmul  and
fdiv  multiply and divide these with a 64-bit intermediate.

Instruction encoding
Every instruction is one 32-bit word with a 6-bit opcode in the top bits, so a single switch
on bits 31–26 decodes everything. There are four formats.
Register fields are 4 bits. Vector registers use the same fields, and values 8–15 fault.
Sign extension. addi , slti , memory offsets and branch offsets sign-extend imm18.
andi , ori  and xori  zero-extend it. Shifts use its low 5 bits.
Branch targets are pc + 4 + (imm18 × 4), a range of about ±512 KB.

Vector
Operands written va , vb , vc  are vector registers; plain a, b, c are scalar registers. vld
and vst  use the I format, vget  and vset  use the I format with the lane number (0–3) as
the immediate, and the rest use the R format.
vdot  sums the four 64-bit lane products, then shifts right by 16. For a three-component
dot product, keep the w lanes at zero.
vxfm  computes each output lane as the dot product of one matrix row with vb: x from
v4 , y from v5 , z from v6 , w from v7 . The result is computed in full before it is written,
so va may be one of the matrix registers.
vproj  maps a transformed vertex to the 320×240 screen:
x = 160 + (160 × x ÷ w), rounded down to a whole pixel
y = 120 − (120 × y ÷ w), rounded down to a whole pixel
z = z ÷ w, as 16.16

Assembler shorthands
Timing and faults
The CPU gets 500,000 cycles per frame, about 30 MHz at 60 fps, and every instruction has
a fixed cost. This is the console's real CPU limit.
Frame loop. A cart does its work for the frame, then executes vsync . The framebuffers
swap, input is sampled, and the cycle counter resets to 500,000.
Overrun. If the budget runs out before vsync , the display repeats the previous frame and
the CPU continues with a fresh budget. A cart that needs between one and two budgets
per frame therefore runs at 30 fps, as slowdown did on real hardware.
What the budget buys. A vertex transform ( vld , vxfm , vproj , vst ) costs 28 cycles. A
worst-case scene of 2,000 triangles with no shared vertices spends about 170,000 cycles
on transforms and roughly 80,000 on building packets. That is half the frame, leaving the
other half for game logic.

Framebuffer. The pixel at (x, y) is the 16-bit value at base + (y × 320 + x) × 2. Which buffer

An 8-bit texture picks one of 16 palettes of 256 colours; palette n starts at colour n ×

A 4-bit texture picks one of 256 palettes of 16 colours; palette n starts at colour n × 16.

Access rules
Only 32-bit access is allowed; byte or halfword access faults.
Reading a write-only register returns 0.
Writing a read-only register faults, as does any access to an offset not listed here.
GPU packets
The GPU understands one thing: a linked list of packets in memory, which it draws in list
order. Sorting is the cart's job, done by choosing where in the list each packet goes.
Header
Every packet starts with one header word.
Type 00  is an empty packet that only links onward. Types the GPU does not recognise are
skipped. A next address outside RAM and ROM faults, as does a list longer than 65,536
packets.
The ordering table
The ordering table is a convention built from empty packets, not something the GPU
knows about. It gives back-to-front drawing without sorting.

1. Reset. Each frame, the cart fills an array of 1,024 empty packets. Entry i links to entry i
− 1, and entry 0 ends the list. This costs about 4,000 cycles.
2. Insert. For each polygon, the cart picks a bucket from its depth, 0 for nearest and 1,023
for farthest. It copies the bucket entry's next address into the new packet, then points
the bucket entry at the new packet.
3. Draw. The cart writes the address of entry 1,023 to GPU_DRAW . The GPU walks from the
farthest bucket to the nearest.
Within one bucket, the most recently inserted packet draws first. Polygons at similar
depths can therefore draw in the wrong order, which is the source of the sorting glitches.
Polygon types
A polygon's type is 20  plus four flags, giving 20 – 2F .
Words

1. Colour: for every vertex if Gouraud, for the first vertex only if flat.
2. Position: always.
3. Texture coordinate: only if textured.

Transparent polygons sort through the ordering table like everything else, so they blend
over whatever was drawn before them.
Drawing rules
Quads are drawn as two triangles, vertices 0-1-2 and 1-2-3, and count as two against
the 2,000 limit.
Palette index 0 is skipped in textured polygons, in both texture depths, whether or not
the packet is semi-transparent.
Clipping is to the screen edges only. Polygons that cross behind the camera must be
dropped or clipped by the cart before projection.
Culling of back faces is the cart's job, which also saves building packets for hidden
faces.
2D drawing (interface, text, sprites) uses textured quads; there is no separate sprite
packet.
Fog
The GPU has no fog. Carts blend each vertex colour toward the fog colour before
submitting, which costs CPU cycles per vertex. Untextured polygons can fog to any
colour. Textured polygons can only fade toward dark colours, because tinting multiplies
the texel. An additive layer drawn over distant geometry is a partial workaround for bright
fog.
Language
Carts are written in a custom, statically typed language that compiles to the CPU's
machine code. The type names are settled; the syntax is not.

The 8- and 16-bit integers exist for memory layout: pixels, texels, packets and sample data.
Arithmetic happens at 32 bits. Proposed: every vector type occupies 16 bytes in memory
with unused lanes zero, so vld  and vst  work on all of them directly.
Features.
No garbage collector. Data is structs and fixed-size arrays in the 2 MB of RAM, so
there are no pauses and the memory limit is real.
Fixed-point literals. A literal such as 0.05  is a fixed  constant; there is no floating
point.
Vector operators. Arithmetic on vector types compiles to vector instructions.
Named registers. A memory-mapped register can be declared with a name and
address, so an assignment to it compiles to a single store.
Standard library. Calls such as camera , mesh  and btn  hide the ordering table, packet
building, fog and input edge detection. Carts can bypass them and build packets by
hand.

Implementation notes
Use SDL3 as the platform layer (window, presenting the framebuffer, audio, controller
input). The emulator rasterizes triangles in its own C code.
What SDL3 is good for
The exact function names are from memory and should be checked against the SDL3 wiki
when work starts.
Trade-off. SDL3 adds to the WebAssembly download. The alternative in the browser is a
small hand-written JavaScript layer using canvas, Web Audio and the Gamepad API. Keep
the platform layer behind three calls (present a frame, queue audio, read input) so either
can be used. Start with SDL3 on desktop, where debugging is fastest.
Structure
The core is plain C with no platform calls. Given a cart, it runs one frame and produces a
320×240 16-bit image and about 368 audio samples.

C pitfalls
Signed overflow is undefined in C. Do add , sub  and mul  on unsigned 32-bit values.
Arithmetic right shift of a negative value is implementation-defined. Implement sar
explicitly.
Division must check for zero and for the most negative number divided by −1 before
dividing.
Rounding down. C division rounds toward zero, but vproj  rounds toward negative
infinity.
Wide intermediates. fmul , fdiv , vmul , vdot  and vxfm  need 64-bit intermediates.
Fill rule. Use integer edge functions with a top-left rule so pixels on a shared edge are
drawn once. Otherwise semi-transparent meshes blend twice along their seams.
Build order
1. Bus and CPU interpreter, with a test per instruction.
2. Assembler, so test programs can be written by hand.
3. GPU rasterizer: flat triangles first, then Gouraud, textures, dither and blending.
4. SDL3 platform layer, to see pixels and press buttons.
5. Audio.
6. Compiler and standard library.
7. WebAssembly build.
